# データソース画面の動線改善 — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | connections-ux |
| 作成日 | 2026-09-29 |
| Issue | [#42](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/42), [#43](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/43) |
| 目的 | 接続テスト結果の表示位置を直し、OAuth 接続の初回セットアップの往復をなくす |

2 件をまとめて扱う。どちらもデータソース画面 (`ConnectionsView` / `ConnectionsRoutes`) の
動線改善で、別作業にすると同じファイルを 2 度触ることになる。

---

## 1. 背景

### 1.1 課題 1: 接続テストの結果でテーブルが崩れる (#42)

#40 で接続テストを htmx 化し、結果を押した行の操作列に差し替える形にした。
しかし結果メッセージが操作列に入るためテーブルのレイアウトが崩れる。

成功メッセージは長い。

```
●Connected: Google Sheets 25.0.9540 / CData JDBC Driver for Google Sheets 2025J 25.0.9540.0
```

失敗時の例外メッセージはさらに長く、操作列に収まるサイズではない。

```kotlin
// web/views/ConnectionsView.kt (現状)
attributes["hx-target"] = "#conn-test-$name"   // ← 操作列の中を差し替えている
```

**副次的な問題:** `hx-target` がボタン自身の親なので、結果が表示されるとボタンが消えて
再テストできない。やり直すにはページの再読み込みが必要。

### 1.2 課題 2: OAuth 認可の導線が保存後にしか出ない (#43)

「OAuth 認可を行う」は `editMode` かつ `existingName != null` のときだけ描画される。

```kotlin
// web/views/ConnectionsView.kt:226
if (editMode) {
    oauthAuthorizationLinkIfNeeded(existingName, existing, propertiesResult)
}
```

そのため新しく OAuth 接続を作るとき、次の往復が必要になる。

1. `/connections/new` でフォームを埋めて保存
2. 一覧に戻される
3. 目的の接続を探して「編集」を開く
4. そこでようやく「OAuth 認可を行う →」が出る

これは**ウィザード側の都合としては妥当**。ウィザードは `/connections/{name}/oauth` で
保存済み設定を読み、認可後は取得したリフレッシュトークンを `saveSharedJdbcConfig` で
同じ名前に書き戻す (#34)。名前が確定していないと成立しない。

つまり「保存前にリンクを出す」のではなく、**保存後に自動でウィザードへ進む**のが筋。

### 1.3 実効 AuthScheme の解決がビューに埋まっている

#43 の判定には実効の AuthScheme が必要。#27 以降、既定値は接続文字列に保存されない
ため `AuthScheme` が URL に無いことが普通に起こる。この「URL の値 → 無ければ
ドライバーの既定値」という解決が現在ビューにインラインで書かれており、
保存ハンドラから使えない。

```kotlin
// web/views/ConnectionsView.kt:352
val authScheme = OAuthCapability.authSchemeOf(config.url)
    ?: properties.properties.firstOrNull { it.propertyName.equals("AuthScheme", ignoreCase = true) }
        ?.defaultValue
```

## 2. 目的

- 接続テストの結果を一覧の上に出し、テーブルを崩さない。結果表示後も再テストできる
- OAuth 接続を新規保存したら、そのまま認可ウィザードへ進む
- 実効 AuthScheme の解決を共有できる形にする

## 3. スコープ

### 3.1 今回実装する機能

| ID | 機能 | 対応 Issue |
|---|---|---|
| F-1 | 接続テスト結果の表示先を一覧テーブルの上のバナーにする | #42 |
| F-2 | 結果メッセージにどの接続のものかを含める | #42 |
| F-3 | 成功・失敗を `success-banner` / `warning-banner` で出し分ける | #42 |
| F-4 | 結果表示後もボタンを残し、再テストできるようにする | #42 |
| F-5 | 実効 AuthScheme の解決を `OAuthCapability` に切り出し、ビューと共用する | #43 |
| F-6 | 新規保存時、ブラウザ認可が必要なら認可ウィザードへリダイレクトする | #43 |

### 3.2 今回実装しない機能 (スコープ外)

| 項目 | 理由 |
|---|---|
| 複数接続の結果を同時に並べる | バナーは 1 つで足りる。直前の結果が消えるのは許容範囲 |
| 結果バナーを閉じるボタン | 次のテストで置き換わり、再読み込みでも消える |
| ドライバー画面のライセンス検証も同じ形にする | あちらは短いバッジでセルに収まっており崩れていない |
| 保存前の OAuth 認可 | ウィザードは保存済み設定の読み書きを前提にしている (#34)。名前が確定していないと成立しない |
| 編集保存後の自動リダイレクト | 編集画面には既にバナーがあり押せば行ける。保存のたびに飛ばされるのは煩わしい |
| 新規フォームへの「OAuth 認可へ」ボタン追加 | AuthScheme は htmx の再描画で変わる。描画時点の判定がずれるため保存時にサーバ側で判定する |

## 4. ユーザーストーリー

| ID | ストーリー |
|---|---|
| US-1 | デモ環境を構築する担当者として、接続テストの結果でテーブルが崩れないでほしい。他の行が読めなくなるため |
| US-2 | デモ環境を構築する担当者として、結果を見た後にもう一度テストしたい。再読み込みせずに試したいため |
| US-3 | デモ環境を構築する担当者として、どの接続の結果か分かるようにしてほしい。結果が行の隣に出なくなるため |
| US-4 | デモ環境を構築する担当者として、OAuth 接続を作ったらそのまま認可に進みたい。一覧に戻されて編集画面を開き直すのは手数が多いため |
| US-5 | デモ環境を構築する担当者として、OAuth を使わない接続では従来どおり一覧に戻ってほしい。認可画面に飛ばされる意味がないため |

## 6. 制約事項

| ID | 制約 |
|---|---|
| C-1 | 接続テストハンドラの応答は HTML 断片のまま。ページ全体を返す形には戻さない |
| C-2 | 画面に例外メッセージや接続文字列を出す場合は必ず `ConnectionStringMasker` を通す |
| C-3 | 実効 AuthScheme の解決はビューから重複を除き、`OAuthCapability` に一本化する |
| C-4 | `OAuthCapability.requiresBrowserAuthorization(String?)` の既存シグネチャは壊さない（#12 のテストが依存） |
| C-5 | ブラウザ認可が必要かの判定基準（対象 AuthScheme の集合）は変更しない |
| C-6 | htmx の使い方は既存の流儀（`DriversView` のライセンス検証、`#36` の削除拒否バナー）に合わせる |

## 7. 影響範囲

| 対象 | 影響 |
|---|---|
| `web/views/ConnectionsView.kt` | 結果バナーの差し替え先を追加。テストボタンの `hx-target` 変更。実効 AuthScheme の解決を共有関数に置き換え |
| `web/routes/ConnectionsRoutes.kt` | 接続テストの応答に接続名とバナークラスを含める。新規保存のリダイレクト先を分岐 |
| `jdbc/OAuthCapability.kt` | 実効 AuthScheme の解決を追加 |
| `config/` | **変更なし** |
| `resources/static/app.css` | **変更不要**（`success-banner` / `warning-banner` は既存） |
| `docs/` | 永続的ドキュメントへの影響なし |
