# 連携一覧画面への削除ボタン追加 — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | syncs-list-delete-button |
| 作成日 | 2026-09-29 |
| 前提 | Phase 2-C (Sync 概念 + Docker API 制御) 完了済み |
| Issue | [#8](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/8) |
| 目的 | 連携一覧画面から連携を削除できるようにし、複数連携の片付けを一覧上で完結させる |

---

## 1. 背景

### 1.1 現状の実装

| 箇所 | 内容 |
|---|---|
| `web/views/TablesView.kt:38` `tablesListView` | 一覧テーブル。列は `名前 / 接続先テーブル / データソース / 状態 / 操作` |
| `web/views/TablesView.kt:381` `tableActions()` | 操作列の中身。稼働中なら「⏸ 停止」、停止中なら「▶ 開始」の**片方のみ**を描画 |
| `web/views/TablesView.kt:117` (詳細画面) | 削除フォームあり。`onsubmit` の JS `confirm` + `POST /syncs/{name}/delete` |
| `web/routes/TablesRoutes.kt:63` `POST /syncs/{name}/delete` | **既存**。Adapter 停止 → Agent コンテナ停止/削除 → `agent.json` 削除 → 設定削除 → `/syncs` へリダイレクト |
| `resources/static/app.css:318` `button.danger` | **定義済みだが未使用**。`background: var(--color-danger)` |

### 1.2 課題

1. **一覧から連携を削除できない**
   削除するには「一覧 → 連携名クリック → 詳細画面 → 削除」と最低 2 画面の遷移が必要。
   デモ環境の構築・片付けでは複数の連携をまとめて消すことが多く、連携ごとに詳細画面を
   往復するのは手数が多い。

2. **削除 API・リダイレクト先は既に一覧向けに用意されている**
   `POST /syncs/{name}/delete` は削除後 `/syncs` にリダイレクトする。
   一覧から呼んでも詳細から呼んでも同じ画面に着地するため、**バックエンド側の変更は不要**。
   一覧画面にボタンが無いだけの状態になっている。

3. **操作列が稼働状態に応じた出し分けになっている**
   `static/app.js` の SSE ハンドラは `tr[data-table]` 内の `.status` セルだけを書き換え、
   操作列は更新しない。そのため稼働状態が SSE で変わっても操作列のボタンは古いままになる
   （開始/停止ボタンに既に存在する挙動）。
   → 新設する削除ボタンは**稼働状態で出し分けない**設計にする必要がある。

## 2. 目的

連携一覧画面の操作列に削除ボタンを追加し、一覧画面だけで連携の削除を完結できるようにする。

## 3. スコープ

### 3.1 今回実装する機能

| ID | 機能 | 内容 |
|---|---|---|
| F-1 | 一覧への削除ボタン追加 | 操作列に「削除」ボタンを追加し、`POST /syncs/{name}/delete` に送信する |
| F-2 | 削除確認ダイアログ | JS `confirm` で確認する。稼働中の Adapter / Agent コンテナ / `agent.json` も削除される旨を明示する |
| F-3 | 稼働中でも削除可 | 稼働状態に関わらず常に削除ボタンを表示する。停止処理は既存の削除ハンドラに任せる |
| F-4 | danger スタイルの適用 | 既存の未使用 `button.danger` を使い、開始/停止ボタンと視覚的に区別する。hover 状態を追加する |

### 3.2 今回実装しない機能 (スコープ外)

| 項目 | 理由 |
|---|---|
| 複数選択による一括削除 | チェックボックス + 一括操作バーが必要になり、変更範囲が一覧テーブル全体に及ぶ。まず 1 件削除の動線を通す |
| 削除完了のフラッシュメッセージ | 現状の Web UI にフラッシュ / トーストの仕組みが無い（`grep` で該当なし）。仕組みの新設は別作業とする |
| 確認画面 (`GET /syncs/{name}/delete/confirm`) の新設 | Drivers 画面・連携詳細画面と同じ JS `confirm` で一貫させる |
| 削除のソフトデリート / 復元 | `ConfigSource.deleteTable()` は物理削除。復元機能は要求されていない |
| CSRF 対策 | 現状の Web UI 全体に CSRF トークンの仕組みが無い。削除ボタン単独で導入しても不完全なので、Web UI 全体の課題として別作業とする |
| 操作列と SSE の同期 (開始/停止ボタンの自動更新) | 既存の挙動であり本作業とは独立。F-3 により削除ボタンはこの問題の影響を受けない |

## 4. ユーザーストーリー

| ID | ストーリー |
|---|---|
| US-1 | デモ環境を構築する担当者として、使い終わった連携を一覧画面から直接削除したい。詳細画面に入り直す手間を省きたいため |
| US-2 | デモ環境を構築する担当者として、稼働中の連携も一覧から削除したい。停止 → 削除の 2 操作を踏みたくないため |
| US-3 | デモ環境を構築する担当者として、削除ボタンを開始/停止ボタンと見間違えたくない。連携の削除は非可逆で、Agent コンテナと `agent.json` まで消えるため |

## 5. 受け入れ条件

| ID | 条件 |
|---|---|
| AC-1 | 連携一覧画面の各行の操作列に「削除」ボタンが表示される |
| AC-2 | 削除ボタンは稼働中・停止中のどちらの連携にも表示される |
| AC-3 | 削除ボタンを押すと確認ダイアログが出る。ダイアログには連携名と、Adapter / Agent コンテナ / `agent.json` も削除される旨が含まれる |
| AC-4 | 確認ダイアログでキャンセルすると何も削除されず、一覧画面に留まる |
| AC-5 | 確認ダイアログで OK すると `POST /syncs/{name}/delete` が実行され、一覧画面に戻る。削除した連携が一覧から消えている |
| AC-6 | 稼働中の連携を削除した場合、Adapter プロセスと Agent コンテナが停止・削除される（既存ハンドラの挙動をそのまま利用） |
| AC-7 | 削除ボタンは `button.danger` で赤く表示され、開始/停止ボタンと視覚的に区別できる。hover 時にも色が保たれる |
| AC-8 | 連携が 0 件のときは従来どおり空状態 (`empty-state`) が表示され、テーブル自体が描画されない |
| AC-9 | 詳細画面の削除ボタンは従来どおり動作する（回帰なし） |
| AC-10 | `./gradlew detekt` と既存テストが通る |

## 6. 制約事項

| ID | 制約 |
|---|---|
| C-1 | `POST /syncs/{name}/delete` のハンドラは変更しない。リダイレクト先 `/syncs` も維持する（詳細画面からの削除も同じ着地点） |
| C-2 | `ConfigSource` インターフェースは変更しない |
| C-3 | 削除ボタンは `form` + `POST` で実装する。Ktor 標準の GET/POST の範囲に収める（既存方針、`TablesView.kt:274` のコメント参照） |
| C-4 | 確認ダイアログのメッセージに連携名を埋め込むため、シングルクォートを含む連携名で JS が壊れないようにする |
| C-5 | 操作列のボタンが増えるため、テーブルの横幅が崩れないこと |
