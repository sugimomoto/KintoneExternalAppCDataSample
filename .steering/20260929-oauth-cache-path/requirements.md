# OAuth キャッシュパスの一本化 — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | oauth-cache-path |
| 対応 Issue | [#11](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/11) |
| 作成日 | 2026-09-29 |
| 目的 | OAuth トークンキャッシュの保存先を全経路で一致させ、接続テストで取得したトークンを実行時にも使えるようにする |
| 後続 | [#12](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/12) Web UI から OAuth 初回認可を完結させる（本件が前提） |

---

## 1. 背景

### 1.1 事象

OAuth 認証のデータソースで、**接続テスト時に取得した OAuth トークンが連携実行時に使われない**。

README のトラブルシューティングは、コンテナ内でブラウザ認可ができない場合の回避策として
「`test-connection` をターミナルから直接実行し、ブラウザで認証してください」と案内している。
この手順でブラウザ認可を通しても、連携を開始すると**もう一度ブラウザ認可が走り**、
コンテナ内ではブラウザが開けず `OAUTH [50001]` で失敗する。

### 1.2 原因

`OAuthSettingsLocation`（CData JDBC Driver のトークンキャッシュ保存先）を付与しているのが
**実行時の `TableAdapterServer` だけ**で、他の経路は `JdbcConfig.url` をそのまま使っている。

| 経路 | ファイル | `OAuthSettingsLocation` | 実際の保存先 |
|---|---|---|---|
| 実行時 Adapter | `runtime/TableAdapterServer.kt:52-54` | ✅ 付与する | `./run/oauth/<連携名>.txt` |
| 接続テスト (Web UI) | `web/routes/ConnectionsRoutes.kt:161` | ❌ | ドライバー既定 |
| 接続テスト (CLI) | `cli/TestConnectionCommand.kt:34` | ❌ | ドライバー既定 |
| テーブル一覧 (CLI) | `cli/ListTablesCommand.kt:33` | ❌ | ドライバー既定 |
| ウィザード Step2 テーブル取得 | `web/routes/TableWizardRoutes.kt:41` | ❌ | ドライバー既定 |
| ウィザード Step3 カラム取得 | `web/routes/TableWizardRoutes.kt:59` | ❌ | ドライバー既定 |
| ウィザード マッピング推奨 | `web/routes/TableWizardRoutes.kt:78` | ❌ | ドライバー既定 |

テストで認可して書き込んだキャッシュと、Adapter が読みに行くキャッシュが別ファイルになる。
Adapter 側から見ればトークン未取得の状態なので、再認可が走る。

### 1.3 課題

1. **接続テストが「本番と同じ条件」になっていない**

   接続テストの目的は「この設定で実行時につながるか」を確かめること。
   キャッシュ先が違えば、テストが通っても実行時に失敗する。

2. **回避策がドキュメントに書かれていない**

   `JdbcUrlEnhancer.withOAuthCachePerTable` はユーザーが接続文字列に
   `OAuthSettingsLocation` を明示していればそれを尊重する実装なので、
   **現状の確実な回避策は自分で書くこと**だが、これはどこにも書かれていない。

3. **同じ抜けが繰り返されている**

   接続文字列のマスク処理も「1 箇所直したが別経路が漏れていた」ことが 2 回起きている
   （#10 → #16）。**規約や文書でなく、型で強制する必要がある。**

### 1.4 調査で判明した事実

| # | 事実 | 詳細 |
|---|---|---|
| F-1 | 接続を張る経路は 7 つある | §1.2 の表。すべて `JdbcConnectionProvider(config)` を直接呼んでいる |
| F-2 | 現在のキャッシュキーは**連携（テーブル）名** | `JdbcUrlEnhancer.cachePathFor(dir, tableName)` → `<dir>/oauth/<連携名>.txt` |
| F-3 | 接続テストとウィザードは連携名を持っていない | 接続テストは「データソース接続」単位、ウィザードは連携作成**前**に動く |
| F-4 | 連携は共通 JDBC 接続を名前で参照できる | `tables.jdbc_ref` → `shared_jdbcs.name`。参照せずインライン設定を持つこともできる |
| F-5 | `ConfigSource` は参照名を外に出していない | `loadTableSet` が `JdbcConfig` に解決してしまい、`jdbc_ref` は捨てられる |
| F-6 | ユーザーの明示指定は尊重される | 接続文字列に `OAuthSettingsLocation` があれば付与しない（既存実装） |

---

## 2. ユーザーストーリー

- **OAuth のデータソースを使う利用者として**、接続テストで一度認可したら、
  連携を開始するときに再認可を求められたくない。

- **利用者として**、同じデータソース接続を複数の連携で使うとき、
  認可は一度で済んでほしい。

- **開発者として**、新しく接続を張る経路を追加したときに、
  キャッシュパスの付与を忘れられない仕組みにしてほしい。

---

## 3. 受け入れ条件

### 3.1 一本化

- [ ] **AC-1** 接続を張るすべての経路で `OAuthSettingsLocation` が同じ規則で付与される
- [ ] **AC-2** キャッシュパスの決定ロジックが 1 箇所にある（経路ごとに重複実装しない）
- [ ] **AC-3** 新しい経路を追加したときに付与を忘れられない（**コンパイルエラーになる**）
- [ ] **AC-4** ユーザーが接続文字列に `OAuthSettingsLocation` を明示した場合は尊重する

### 3.2 キャッシュの単位

- [ ] **AC-5** 同じデータソース接続を参照する複数の連携が、同一のキャッシュを共有する
- [ ] **AC-6** 接続テスト・ウィザード・実行時が同一のキャッシュを指す
- [ ] **AC-7** インライン JDBC 設定の連携でも動作する（共有接続を参照しない場合）

### 3.3 品質

- [ ] **AC-8** キャッシュキーの決定にユニットテストがある
- [ ] **AC-9** パス区切り文字を含む名前でディレクトリを抜け出さない
- [ ] **AC-10** `./gradlew test` が通り、本変更で lint の指摘が増えない
- [ ] **AC-11** 既存キャッシュの扱い（移行の必要性）がドキュメントに書かれている

---

## 4. 制約事項

| # | 制約 | 理由 |
|---|---|---|
| C-1 | キャッシュパスの決定を経路ごとに書かない | #10 → #16 で「1 箇所直して別経路が漏れる」を 2 回繰り返している |
| C-2 | 文書や規約による「必ず通すこと」に頼らない | 同上。マスク処理はこの方式で 2 回漏れた（C-1 の教訓） |
| C-3 | ユーザーの明示指定を上書きしない | F-6 の既存挙動を壊さない（AC-4） |
| C-4 | 保存済みの接続文字列を書き換えない | 設定の保存内容は変えない。付与は**接続を張るときだけ** |
| C-5 | 連携名・接続名をそのままパスに使わない | `/` や `..` でディレクトリを抜け出せる（AC-9） |

## 5. スコープ外

| 項目 | 扱い |
|---|---|
| Web UI からの OAuth 初回認可 | [#12](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/12) |
| 既存キャッシュの自動移行 | 連携名 → 接続名の対応は多対一で一意に決まらない。一度の再認可で解決するため移行しない（ドキュメントに明記） |
| OAuth 以外の認証方式への影響 | `OAuthSettingsLocation` は OAuth 系のみ有効。他方式では無害 |
