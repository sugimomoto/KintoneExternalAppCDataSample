# ウィザードの失敗を画面に出す — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | wizard-error-visible |
| 作成日 | 2026-10-05 |
| Issue | [#64](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/64) |
| 目的 | 連携追加ウィザードの失敗を画面に表示し、原因が分かる状態にする |

---

## 1. 背景

### 1.1 課題

連携追加ウィザードの step4 で例外が発生すると**画面が真っ白**になる。原因が画面から
一切分からず、ログを見ないと手が出ない。

```
java.lang.IllegalStateException: 主キーが定義されていません: Customer
Unhandled: POST - /syncs/new/step4
500 Internal Server Error: POST - /syncs/new/step4 in 105ms
```

### 1.2 原因

ルートが例外を投げるだけでハンドリングしていない。

```kotlin
// web/routes/TableWizardRoutes.kt
val pk = inspector.findPrimaryKey(tableName, schema)
    ?: throw IllegalStateException("主キーが定義されていません: $tableName")
```

Ktor の既定動作で 500 が返り、本文が空になる。Web UI 全体に例外ハンドラ
（`StatusPages`）が設定されていない。

### 1.3 主キーが無い場合は「連携できない」が正しい

`kintone-external-app-spec` で確認した。**読み取り専用であっても連携できない。**

| メソッド | 必須/任意 | ID の要求 |
|---|---|---|
| `GetCapability` | **必須** | `RecordIdType record_id_type = 9`（NUMBER / TEXT）の宣言 |
| `GetSchema` | **必須** | `RecordIdFieldDefinition` |
| `Insert` | 任意 | 発行した ID を**返す**必要がある |
| `Update` | 任意 | Record に ID フィールドが必須 |
| `Delete` | 任意 | `ids` / `record_ids` で指定 |
| `Select` / `Count` / `Search` / `Aggregate` | 任意 | ID 自体は不要 |

`Insert` / `Update` / `Delete` は任意なので実装しない選択はできるが、`GetSchema` が
レコード ID フィールドを返せないと設定画面の段階で成立しない。

kintone 側の制約表にも明記されている。

> レコード番号 | ○ | BIGINT 型カラムのみ指定可（NUMBER ID時）／TEXT ID 時は VARCHAR

したがってエラーメッセージは「主キーが見つかりません」ではなく、**連携できない理由と
根拠**を伝えるべき。

### 1.4 #63 との関係

#63（スキーマ対応）でスキーマを渡すようになり、「スキーマを渡していないために
主キーが見つからない」という不具合は解消した。しかし**本当に主キーの無いテーブルや
ビューを選んだ場合は依然として真っ白になる**。本 Issue はそこを扱う。

## 2. 目的

ウィザードで想定しうる失敗を画面に表示し、利用者が次の行動を取れるようにする。

## 3. スコープ

### 3.1 今回実装する機能

| ID | 機能 |
|---|---|
| F-1 | 主キーが見つからない場合、専用の案内を画面に出す（連携できない理由と根拠を含む） |
| F-2 | メタデータ取得の失敗も画面に出す |
| F-3 | 例外メッセージは `ConnectionStringMasker` を通す |
| F-4 | 失敗時も前のステップに戻れるようにする |

### 3.2 今回実装しない機能 (スコープ外)

| 項目 | 理由 |
|---|---|
| Web UI 全体への `StatusPages` 導入 | 影響範囲が広い。まずウィザードの失敗を見えるようにする |
| レコード ID 列を利用者が選べるようにする | [#66](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/66) で別途。本 Issue のエラー画面を発展させる形になる |
| 主キーの無いテーブルを連携できるようにする | 仕様上成立しない（§1.3） |

## 4. ユーザーストーリー

| ID | ストーリー |
|---|---|
| US-1 | 検証を進める担当者として、テーブルを選んで進めなかった理由を画面で知りたい。真っ白では何が起きたか分からず、ログを見る前提になるため |
| US-2 | 検証を進める担当者として、連携できないテーブルだと分かったら別のテーブルを選び直したい。戻る導線が無いとブラウザバックに頼ることになるため |
| US-3 | 検証を進める担当者として、なぜ主キーが必要なのか理由を知りたい。kintone 側の制約だと分かれば、DB 側を直すか別のテーブルにするか判断できるため |

## 5. 受け入れ条件

| ID | 条件 |
|---|---|
| AC-1 | 主キーが見つからないテーブルを選んだとき、HTTP 200 で画面に理由が表示される |
| AC-2 | 表示にどのテーブルで起きたかが含まれる |
| AC-3 | kintone がレコード番号を必須とするため連携できない旨が示される |
| AC-4 | 画面が真っ白にならず、前のステップに戻れる |
| AC-5 | メタデータ取得が失敗した場合も画面に理由が出る |
| AC-6 | 例外メッセージに接続文字列が含まれる場合はマスクされる |
| AC-7 | 正常なテーブルでは従来どおり step4 に進む |
| AC-8 | `./gradlew test` が通り、detekt が 83 件以下である |

## 6. 制約事項

| ID | 制約 |
|---|---|
| C-1 | ウィザードのステップ構成（step1〜step4）は変えない |
| C-2 | 画面に例外メッセージを出す場合は必ず `ConnectionStringMasker` を通す（既存方針） |
| C-3 | メッセージはロケール依存の例外文をパースして分類しない（#19 の方針） |
| C-4 | 既存の `warning-banner` を使う。新しいスタイルは追加しない |
| C-5 | #66 で「列を選ぶ画面」に発展させられる構造にする（エラー表示をハードコードで埋め込まない） |

## 7. 影響範囲

| 対象 | 影響 |
|---|---|
| `web/routes/TableWizardRoutes.kt` | step4 の例外を結果型に変える |
| `web/views/TableWizardView.kt` | 失敗時の表示を追加 |
| `docs/` | 永続的ドキュメントへの影響なし（UI の表示追加） |
