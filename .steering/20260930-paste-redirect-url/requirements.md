# リダイレクト URL の貼り付け対応 — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | paste-redirect-url |
| 作成日 | 2026-09-30 |
| Issue | [#57](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/57) |
| 目的 | 認可コードの手作業での切り出しをなくし、リダイレクト先 URL をそのまま貼れるようにする |

---

## 1. 背景

### 1.1 現状の実装

| 箇所 | 内容 |
|---|---|
| `web/views/ConnectionOAuthView.kt:117` | 「Step 2: 認可コードを貼り付ける」 |
| `web/views/ConnectionOAuthView.kt:135` | ラベル「認可コード (code= の値):」 |
| `web/views/ConnectionOAuthView.kt:123` | 案内「code= の後ろの値（次の & まで）をコピーする」 |
| `web/routes/ConnectionOAuthRoutes.kt:52` | `verifier` をそのままプロシージャに渡す |

### 1.2 課題

入力が **`code=` の値だけ**を前提にしており、利用者に手作業での切り出しを求めている。

実際のリダイレクト先 URL はこうなる。

```
http://localhost:33333/?iss=https://accounts.google.com&code=4/0AXlqoi7hDZMDQCLQs-ZalS0Oe94xyiwXwsiF1hLVULlJbnO7cAJdYHJKILGXZ100fUdeeg&scope=https://www.googleapis.com/auth/spreadsheets%20https://www.googleapis.com/auth/drive
```

`code=` は途中にあり、前後に `iss=` と `scope=` が付く。**URL 全体をコピーしてから該当部分だけを切り出す**のは手間で、範囲を誤ると**認可コードは 1 回しか使えない**ためやり直しになる。

## 2. 目的

リダイレクト先 URL をそのまま貼り付けて認可を完了できるようにする。

## 3. スコープ

### 3.1 今回実装する機能

| ID | 機能 |
|---|---|
| F-1 | 入力に `code=` が含まれていれば、その値を取り出して使う |
| F-2 | 含まれていなければ入力全体を認可コードとして扱う（従来どおり） |
| F-3 | パーセントエンコードを解く |
| F-4 | `error=` を含む URL が貼られた場合はその内容を伝える |
| F-5 | ラベルと案内文を「URL をそのまま貼れる」表現に変える |

### 3.2 今回実装しない機能 (スコープ外)

| 項目 | 理由 |
|---|---|
| リダイレクトを受け取るローカルサーバの実装 | 貼り付け自体を省けるが、ポート衝突と「コンテナ内からブラウザのホストを listen できない」問題がある。別途検討 |
| 認可コードの形式バリデーション | プロバイダごとに形式が違う。誤りはトークン取得時のエラーで分かる |
| クリップボードからの自動読み取り | ブラウザの権限が必要で、貼り付け 1 回と比べて利点が小さい |
| `state` の検証 | 本サンプルは利用者自身が URL を貼る手動フローで、CSRF の攻撃面が通常の OAuth と異なる。Web UI 全体の CSRF 対策と併せて別途検討 |

## 4. ユーザーストーリー

| ID | ストーリー |
|---|---|
| US-1 | デモ環境を構築する担当者として、リダイレクト先の URL をそのまま貼りたい。`code=` の範囲を目で探して選択するのは手間で、認可コードは 1 回しか使えないため失敗するとやり直しになるため |
| US-2 | デモ環境を構築する担当者として、認可コードだけを貼る従来の使い方も続けたい。既に手元にコードがある場合に使えないと困るため |
| US-3 | デモ環境を構築する担当者として、認可を拒否した場合にその理由が分かるようにしてほしい。`error=access_denied` の URL を貼って「コードが不正」と言われると原因が分からないため |

## 5. 受け入れ条件

| ID | 条件 |
|---|---|
| AC-1 | リダイレクト先 URL をそのまま貼り付けて認可を完了できる |
| AC-2 | `code=` が途中にあり前後に他のパラメータがある URL から正しく抽出できる |
| AC-3 | 認可コードだけを貼り付けても従来どおり動く |
| AC-4 | パーセントエンコードされた値が解かれる |
| AC-5 | `+` が空白に変換されない |
| AC-6 | `error=` を含む URL を貼った場合、その内容が画面に出る |
| AC-7 | 入力欄のラベルと案内文が「URL をそのまま貼れる」ことを示す |
| AC-8 | 認可コード・URL がログに出ない（#12 の方針を維持） |
| AC-9 | 抽出ロジックに単体テストがある |
| AC-10 | `./gradlew test` が通り、detekt がベースライン 84 件のままである |

## 6. 制約事項

| ID | 制約 |
|---|---|
| C-1 | 抽出は純粋関数として切り出し、DB もドライバーも要らずテストできること |
| C-2 | テストケースには**実際に観測された URL 形式**を使う。推測で作らない |
| C-3 | `+` を空白に変換してはいけない。OAuth の認可コードに `+` が含まれる場合に壊れる |
| C-4 | 入力値（URL 全体）をログに出さない。認可コードを含むため（#12） |
| C-5 | 例外メッセージに認可コードが混ざる場合は `OAuthUrlMasker.redactVerifier` で伏せる（既存方針） |
| C-6 | `OAuthAuthorizer` / `OAuthProcedureSql` のインターフェースは変えない |

## 7. 影響範囲

| 対象 | 影響 |
|---|---|
| `jdbc/AuthorizationCodeExtractor.kt` | 新規。URL または素のコードから `code` を取り出す |
| `web/routes/ConnectionOAuthRoutes.kt` | 入力を抽出してから渡す。`error=` の場合の分岐 |
| `web/views/ConnectionOAuthView.kt` | ラベルと案内文 |
| `jdbc/OAuthAuthorizer.kt` / `OAuthProcedureSql.kt` | **変更なし**（C-6） |
| `docs/` | 永続的ドキュメントへの影響なし |
