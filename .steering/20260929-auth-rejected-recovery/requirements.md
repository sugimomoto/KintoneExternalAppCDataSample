# 接続キー拒否からの復旧導線 — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | auth-rejected-recovery |
| 対応 Issue | [#21](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/21) |
| 作成日 | 2026-09-29 |
| 前提 | [#19](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/19) 自動停止 / [#20](https://github.com/sugimomoto/KintoneExternalAppCDataSample/issues/20) 状態の可視化 |
| 目的 | 接続キーを拒否された連携を、画面から復旧できるようにする |

---

## 1. 背景

### 1.1 一連の対応の最後のピース

| Issue | 役割 | 状態 |
|---|---|---|
| #19 | 直らない再試行を**止める** | 完了 |
| #20 | 異常に**気付ける**ようにする | 完了 |
| **#21** | **直せる**ようにする | 本件 |

#19 / #20 の結果、いま 3 連携（Product / ProductPlant / bcartorders）が
一覧で「停止中」と表示されている。状態は見えるが、**復旧手段が画面にない**。

### 1.2 現状の実装

| 箇所 | 内容 |
|---|---|
| `agent/SyncConnectionService.kt` | `AUTH_FAILED` を `Result.Failure(reason)` に畳んでいる。他の失敗と区別できない |
| `web/routes/ConnectKintoneRoutes.kt` | `Failure` のとき `connectKintoneView(error = reason)` を再描画する。**トークン入力欄は残る** |
| `web/views/TablesView.kt` | Agent バッジは `停止中`。停止の**理由は分からない** |
| `web/views/HelpView.kt` | 「4. kintone と接続」に手順の記載がある |

### 1.3 課題

1. **なぜ止まっているのかが分からない**

   #19 で自動停止するようになったため、利用者が見るのは「停止中」だけ。
   認証拒否で止められたのか、手で止めたのかが区別できない。
   `docker logs` を見るまで原因に辿り着けない。

2. **停止理由が console の再起動で失われる**

   #19 の棚卸しは「直近 3 分のログ」で判定する。いったん停止したコンテナは
   ログを出さなくなるので、**次の起動時には検知されない**。
   つまり停止直後の 1 回しか理由が分からない。

3. **復旧の入口が連携詳細から見つけにくい**

   接続画面 (`/syncs/{name}/connect`) には「kintone と接続」ボタンから行けるが、
   連携詳細には「接続キーが拒否されている」という文脈がないため、
   そのボタンを押すべきだと気付けない。

4. **kintone 側で何をすべきかが画面にない**

   現在のメッセージは「kintone 側で接続キーを再発行し、入力し直してください」だけ。
   どの画面のどの操作かは書かれていない。

### 1.4 調査で判明した事実

| # | 事実 | 詳細 |
|---|---|---|
| F-1 | 接続画面は再入力可能な状態で再描画される | `Failure` のとき `connectKintoneView(error = ...)` を返し、Step 2 のトークン入力欄はそのまま残る |
| F-2 | `Result` は 3 種類 | `Success` / `Pending(reason)` / `Failure(reason)`。認証拒否専用の型はない |
| F-3 | 認証拒否の検知箇所は 2 つ | 接続操作時 (`SyncConnectionService`) と console 起動時 (`AgentAuthFailureSweeper`) |
| F-4 | 実行時状態の永続化に前例がある | `runtime/ActiveAdaptersFile` が `run/active-adapters.json` に JSON で書き出す |
| F-5 | ヘルプ画面に接続手順がある | `HelpView` の「4. kintone と接続」。鍵ペア生成 → 公開鍵登録 → JWT 入力の流れ |
| F-6 | 設定は SQLite に一本化済み | `config.db` は連携の**設定**を持つ。実行時の状態は対象外 (#5) |

## 2. ユーザーストーリー

- **運用者として**、連携が止まっている理由を画面で知りたい。
  「停止中」だけでは、放置していいのか対処が必要なのか分からない。

- **運用者として**、接続キーが拒否されている連携から、復旧操作にすぐ移りたい。
  どの画面へ行けばいいか探したくない。

- **運用者として**、kintone 側で何をすればいいのかを画面で確認したい。
  手順書を別に開きたくない。

- **運用者として**、console を再起動しても停止理由が残っていてほしい。
  翌日出社したときに理由が消えていると困る。

---

## 3. 受け入れ条件

### 3.1 理由の記録

- [ ] **AC-1** 接続キーを拒否されたことが記録され、console を再起動しても残る
- [ ] **AC-2** 接続操作で拒否されたときと、起動時の棚卸しで検知したときの両方で記録される
- [ ] **AC-3** 接続が成立したら記録が消える
- [ ] **AC-4** 記録に接続キー本体を含めない

### 3.2 表示と導線

- [ ] **AC-5** 連携一覧で「接続キーが拒否されて止まっている」ことが分かる（単なる「停止中」と区別できる）
- [ ] **AC-6** 連携詳細に、拒否されている旨と検知時刻が出る
- [ ] **AC-7** 連携詳細から接続画面へ 1 クリックで移動できる
- [ ] **AC-8** kintone 側で何をすべきかが画面に書かれている（ヘルプへの導線を含む）
- [ ] **AC-9** 接続画面で接続キーを再入力して再接続できる

### 3.3 復旧

- [ ] **AC-10** 再入力して接続が成立すれば Agent が稼働状態に戻り、一覧の表示も変わる
- [ ] **AC-11** 認証拒否と、それ以外の失敗（Adapter 未到達・タイムアウト）で案内が出し分けられる

### 3.4 品質

- [ ] **AC-12** 記録の読み書きにユニットテストがある
- [ ] **AC-13** 記録ファイルが壊れていても画面が落ちない
- [ ] **AC-14** `./gradlew test` が通り、本変更で lint の指摘が増えない

---

## 4. 制約事項

| # | 制約 | 理由 |
|---|---|---|
| C-1 | 接続キーを記録・ログに残さない | #10 / #16 の方針。記録するのは理由と時刻のみ（AC-4） |
| C-2 | 記録は `config.db` に入れない | `config.db` は連携の設定を持つ。実行時の状態は `run/` 配下に置く既存の流儀に合わせる（F-4, F-6） |
| C-3 | 記録の読み取り失敗で画面を落とさない | 補助情報のため。壊れたファイルは「記録なし」として扱う（AC-13） |
| C-4 | 認証拒否を専用の型で表す | `Failure(reason)` の文言で判定するのは壊れやすい（F-2, AC-11） |
| C-5 | 画面の呼称を新設しない | 開発ガイドライン 3.5.1 |

---

## 5. スコープ外

| 項目 | 扱い |
|---|---|
| kintone API を使った接続キーの自動再発行 | kintone 側の管理画面操作が前提。自動化は別途判断 |
| 接続キーの有効期限の事前警告 | 拒否の原因は期限切れとは限らない（#19 の調査結果）。別途判断 |
| 認証以外の失敗理由の永続化 | 一過性の失敗は記録する価値が薄い。認証拒否だけを扱う |
| 通知（メール・Slack 等） | 画面で分かれば足りる |
