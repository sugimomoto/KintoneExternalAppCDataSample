# テーブル選択のページネーション + 検索 — 要求定義

| 項目 | 内容 |
|---|---|
| 開発タイトル | table-list-pagination-search |
| 作成日 | 2026-09-29 |
| 前提 | Phase 2-C (Sync 概念 + Docker API 制御) 完了済み |
| 目的 | New Sync ウィザード Step 2 で、テーブル数の多いデータソースでも目的のテーブルを選択できるようにする |

---

## 1. 背景

New Sync ウィザードの Step 2「Select Table」は、JDBC 接続先のテーブル・ビュー一覧を
ラジオボタンのリストで表示している。現状の実装には以下の制約がある。

### 1.1 現状の実装

| 箇所 | 内容 |
|---|---|
| `web/routes/TableWizardRoutes.kt` `get("/syncs/new/step2")` | `JdbcMetadataInspector.listTables()` で**全件**取得し、そのまま View に渡す |
| `web/views/TableWizardView.kt:97` | `tables.take(100)` で**先頭 100 件のみ**を描画 |
| `web/views/TableWizardView.kt:94` | 表示文言 `"Found ${tables.size} tables (showing first 100)"` |
| `resources/static/app.css` `.scrollable-list` | `max-height: 360px` の縦スクロールリスト |

### 1.2 課題

1. **101 件目以降のテーブルが選択できない**
   件数自体は「Found 1,043 tables」と表示されるため存在は分かるが、UI 上から到達する手段がない。
   Salesforce (標準 + カスタムオブジェクトで数百〜1000 超)、Snowflake、Google Sheets の
   複数スプレッドシートなど、CData JDBC Driver の主要データソースで容易に上限を超える。
   → **回避策がなく、実質的に連携作成のブロッカーになる。**

2. **目的のテーブルを探せない**
   100 件以内に収まる接続でも、スクロールリストから目視で探す必要がある。
   ブラウザの Ctrl+F はスクロール領域内を検索できるが、テーブル名を正確に知らないと使えない。

3. **Step 2 表示のたびにメタデータを全件取得している**
   `getTables(null, null, "%", ...)` をページ表示のたびに実行する。
   テーブル数の多いデータソースでは Step 2 の初回表示が遅くなる。

## 2. 目的

Step 2 のテーブル選択に**検索**と**ページネーション**を追加し、
テーブル数に関係なくすべてのテーブルを選択可能にする。

## 3. スコープ

### 3.1 今回実装する機能

| ID | 機能 | 内容 |
|---|---|---|
| F-1 | テーブル検索 | テーブル名・スキーマ名に対する部分一致・大文字小文字無視の絞り込み |
| F-2 | ページネーション | 件数制限を撤廃し、ページ単位で全テーブルにアクセス可能にする |
| F-3 | 件数表示 | 「全 N 件中 X〜Y 件を表示」および検索時のヒット件数表示 |
| F-4 | 部分更新 | 検索・ページ移動時は htmx でリスト部分のみを差し替える (全画面リロードしない) |
| F-5 | メタデータキャッシュ | 検索・ページ移動のたびに JDBC メタデータを再取得しない |

### 3.2 今回実装しない機能 (スコープ外)

- Step 3「Select Columns」のカラム一覧のページネーション・検索
  (カラム数は通常数十件で、現状 `take` による制限もかかっていないため)
- テーブル種別 (TABLE / VIEW) でのフィルタリング
- スキーマ単位のグルーピング表示
- 複数テーブルの一括選択 (1 Sync = 1 テーブルの前提は変更しない)

## 4. ユーザーストーリー

- **US-1**: 運用者として、Salesforce 接続で `Opportunity` テーブルを連携したい。
  テーブル一覧が 1000 件を超えていても、検索ボックスに `oppo` と入力すれば
  候補が絞り込まれ、目的のテーブルを選択できる。

- **US-2**: 運用者として、正確なテーブル名を覚えていない場合でも、
  ページを送りながら一覧を眺めてテーブルを探せる。

- **US-3**: 運用者として、検索やページ移動をしても Step 1 で選んだ Connection や
  入力途中の Config name が失われないでほしい。

## 5. 受け入れ条件

| ID | 条件 |
|---|---|
| AC-1 | テーブルが 100 件を超えるデータソースで、101 件目以降のテーブルを選択して Sync を作成できる |
| AC-2 | 検索ボックスに文字列を入力すると、テーブル名またはスキーマ名に部分一致するテーブルのみが表示される (大文字小文字を区別しない) |
| AC-3 | 検索結果が 1 ページに収まらない場合、検索条件を維持したままページ移動できる |
| AC-4 | 「全 N 件中 X〜Y 件」形式で現在の表示範囲が分かる。検索時は絞り込み後の件数を表示する |
| AC-5 | 検索・ページ移動を行っても、入力済みの Config name が保持される |
| AC-6 | 検索結果が 0 件の場合、その旨のメッセージが表示される (空のリストにならない) |
| AC-7 | 検索・ページ移動のたびに JDBC メタデータの再取得が発生しない |
| AC-8 | 既存の E2E テスト (`NewSyncFlowE2ETest`) が通る、または新 UI に合わせて更新されている |
| AC-9 | `./gradlew detekt test` が通る |

## 6. 制約事項

- **既存の画面構成 (4 ステップウィザード) は変更しない。** Step 2 の内部 UI のみを改修する。
- **サーバサイドレンダリング + htmx の方針を維持する。** SPA フレームワークは導入しない。
  (`web/views/Layout.kt:42` で htmx は読み込み済み)
- **`JdbcMetadataInspector` の既存 API (`listTables()`) は後方互換を維持する。**
  `cli/InitTableCommand.kt` からも利用されている。
- **絞り込みはアプリケーション側で行う。** データソースごとに `getTables` のパターン指定の
  挙動が異なるため、JDBC 側にフィルタを委譲しない。
- キャッシュは Connection 単位で行い、テーブル構成の変更に追従できるよう
  手動での再取得手段 (Refresh) を用意する。

## 7. 未確定事項 (design.md で決定する)

- デフォルトのページサイズ (50 / 100 のいずれか、ユーザーによる切替可否)
- キャッシュの保持方式 (インメモリ / TTL / ウィザードセッション単位) と有効期限
- 検索のトリガ (インクリメンタル検索か、検索ボタン押下か)
